# WILL. 个人网站架构与专业度审查

审查日期：2026-07-28
审查范围：当前单页网站的内容定位、信息架构、前端实现、动效可靠性、响应式表现、可访问性、证据可信度、搜索与分享能力，以及未来扩展方式。

## 一、结论摘要

当前版本已经从“视觉型学生主页”升级为“有明确方向、有成果证据、有完整叙事的第一学年个人作品站”。最强的部分不是经历数量，而是已经形成了一条连贯主线：

> 用代码构建 → 用模型分析 → 进入真实场景调研 → 把答案讲清楚

这条主线能够同时容纳量化开发、金融科技后端、数学建模、田野调研与英语表达，也避免把网站写成面向家教的广告页。对于大一结束阶段，内容密度和可信度已经足够；下一阶段应优先提高运行可靠性、移动端体验和项目证据深度，而不是继续堆叠宽泛技能词。

## 二、当前架构画像

### 1. 技术结构

- 形态：静态单页网站，当前部署在 Vercel。
- 主页面：`index.html`，约 123 KB、2,799 行。
- 主样式：`will-tech.core.v1.css`，约 111 KB、6,160 行；页面内另有 7 个内联样式块。
- 动效与交互：Webflow 运行时代码、GSAP、SplitText、ScrollTrigger、InertiaPlugin、Draggable、Lenis、anime.js、Unicorn Studio，以及少量原生 IntersectionObserver。
- 内容证据：两个本地脱敏奖项文件与一个南方+外部新闻链接。
- 质量保障：基线 18 项 Node 静态回归测试，以及 Playwright 浏览器 QA 脚本；工程化分支另新增 5 项构建契约。
- 数据与服务：没有数据库、用户账户、服务端 API 或内容管理系统。

### 2. 信息架构

```text
首页主张
├─ Academic Background：身份与年级
├─ Current Focus：量化开发 × 金融科技后端
├─ Experience：四段横向经历
│  ├─ Build & Deploy
│  ├─ Mathematics & Leadership
│  ├─ County Development
│  └─ English & Communication
├─ Methods & Skills：四组方法与工具
├─ About：学校、个人、学院环境
└─ Contact：邮箱与微信
```

这个顺序是合理的：先回答“是谁、在做什么”，再用经历证明，随后总结方法，最后补足身份与联系方式。横向经历是网站的核心，而不是装饰性时间轴。

## 四、专业内容审查

### 1. 当前定位为什么成立

“量化开发 × 金融科技后端”是一个方向声明，而不是超出阶段的职业自封。后续内容提供了三层支撑：

1. 工具层：Python 数据处理、C++ 与算法、Web 与部署、Git 与 LaTeX。
2. 方法层：建模、工程实现、结果检验、结构化写作、团队协作。
3. 证据层：完整上线的网站、全国建模竞赛奖项、省级调研和公开报道、英语演讲奖项。

网站没有把 `pandas`、`yfinance` 或“基础策略验证”包装成成熟量化研究成果，这一点克制且可信。下一步如果要强化量化开发，应优先加入可运行的工程项目，而不是继续扩写“研究”“策略”“因子”等词。

### 2. 四段经历的呈现逻辑

- **Build / Ship** 证明独立交付能力，是“能把东西做出来”。
- **Model / Lead** 证明数学建模与组长职责，是“能拆解问题并组织协作”。
- **Field / Research** 证明进入现实场景、处理一手材料与协作文书，是“能理解问题发生的环境”。
- **Speak / Connect** 证明英语表达与跨文化沟通，是“能把结论讲清楚”。

四段经历不是同一类型的奖项罗列，而是完整的问题解决链条。这比单纯增加第五、第六段经历更高级，也更适合后续把真正的项目替换进去。

### 3. 证据强度与用词边界

建议长期维持以下证据分级：

| 证据级别 | 可使用的表述 | 当前实例 |
| --- | --- | --- |
| A：公开第三方来源 | 可写明确项目、范围、奖项或公开发布结果 | 南方+报道 |
| B：脱敏正式凭证 | 可写奖项名称、级别、时间与个人/团队职责 | 建模全国三等奖、CN Stories 广东省级二等奖 |
| C：可运行作品或仓库 | 可写技术栈、个人实现范围、结果指标 | 当前网站；未来 GitHub 项目 |
| D：自述经历 | 宜写“参与、协作、学习、完成”，避免写成主导或专业结论 | 法国留学生接待、课程学习 |

“共同负责”“参与新闻稿初稿撰写”比“主导新闻发布”准确；“随院长领衔的跨学科团队”比单写“跟随院长调研”更专业，也不借用院长身份制造权威感。

### 4. 物理能力如何处理

公共个人网站不应为了家教目的单独增加物理或“授课能力”入口。只有当未来出现课程项目、实验报告、竞赛或可公开作品时，再把物理作为项目证据自然加入；现阶段不额外设置“数学 / 物理 / 英语”授课标签，避免削弱量化开发主线。

## 六、推荐的目标架构

近期不需要为“高级感”引入后端。更适合的目标是“静态生成 + 模块化源码 + 自动化验证”：

```text
content/
├─ profile.json
├─ experiences.json
└─ skills.json

src/
├─ sections/
├─ motion/
├─ styles/
└─ utilities/

public/
├─ images/
└─ evidence/

tests/
├─ content
├─ motion-contract
└─ browser-qa

构建输出 → 静态 HTML/CSS/JS → Vercel
```

是否使用 Astro、Vite 或其他工具不是重点。验收标准是：内容只有一个数据来源、每个动效只有一个控制器、构建后仍是可静态托管的网站、外部依赖失败时基本内容可读。

### 什么时候不需要后端

以下功能都不需要传统后端服务器：

- 展示个人介绍、经历、图片和证书；
- 链接 GitHub、论文、新闻、演示站和其他项目；
- 展示代码片段或静态生成的项目详情；
- 托管纯前端可运行 demo；
- 使用第三方表单服务接收简单联系信息；
- 使用 GitHub Actions 验证并通过 Vercel Preview 审核部署候选。

### 什么时候才需要后端或 Serverless

- 用户注册、登录与私有账户；
- 持久保存用户数据、评论、收藏或进度；
- 需要数据库实时查询；
- 需要受保护的后台内容编辑；
- 联系表单必须由你自己的服务处理、校验和防滥用；
- 调用带私钥的 API，且密钥不能暴露给浏览器；
- 需要权限控制、支付、审计或个性化内容。

因此，展示代码或连接其他项目与后端没有必然关系。下一阶段先完善静态项目页、GitHub 链接和可运行 demo，收益远高于提前接入账户系统。

## 七、分阶段改进路线

### P0：可靠进入网站（S，建议优先）

目标：动画运行时缺失时立即释放；其他未知异常最迟由 8 秒 watchdog 释放，用户能够看到可滚动的完整内容。

验收：

- 阻断所有第三方请求后，预加载器自动退出；
- 页面不锁滚动；
- 正文、证据链接和联系方式可操作；
- 控制台没有导致后续脚本中断的未捕获错误。

### P1：移动端与交互语义（M）

目标：手机和键盘用户不依赖猜测完成浏览。

验收：

- 360 / 390 / 768px 的经历全部可连续阅读；
- 菜单入口为真正按钮，Tab、Enter、Esc 和焦点回收正常；
- 所有 `href="#"` 被真实链接、按钮或非交互容器替代；
- 通过基础 Lighthouse Accessibility 人工复核。

### P2：工程拆分与性能（M–L）

目标：以后增加项目时，不再直接编辑近 3,000 行单文件。

验收：

- 内容、样式、动效控制器分离；
- 每个元素只有一个动效所有者；
- 删除未使用运行库；
- 关键资源本地化或具备失败回退；
