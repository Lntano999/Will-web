# Will-web 工程化知识笔记

这份笔记记录网站产品化与工程化过程中，真正影响方案选择、风险判断和验收结果的专业概念。它不是独立课程，也不追求一次写全；后续随着实际迁移、测试和发布逐步补充。

## 需求与设计

### Spec（规格说明）

**是什么：** Specification 的简称，定义产品要达到的结果、范围边界、系统结构和验收标准。

**在 Will-web 中：** 当前 spec 会明确保留哪些视觉和动效、为什么采用 Vite 渐进迁移、每个阶段怎样判断成功，以及发生事故时如何回滚。

**为什么重要：** 它防止 AI 或开发者只凭“看起来更专业”进行无边界重构。Spec 主要回答“做成什么”。

### Implementation Plan（实施计划）

**是什么：** 把已经确认的 spec 拆成可执行步骤，注明修改文件、测试命令、预期结果和提交节点。

**在 Will-web 中：** 只有 spec 经用户复核后才会编写计划。计划主要回答“按什么顺序做、每一步怎样验证”。

**为什么重要：** 设计和施工分开，可以在代码改动前发现遗漏，也能让每批变更独立验证和回滚。

### Acceptance Criteria（验收标准）

**是什么：** 判断一个阶段是否真正完成的可观察条件，而不是“应该差不多”“代码能跑”等主观描述。

**在 Will-web 中：** 例如外部资源全部阻断时预加载器仍能释放、六档视口内容可读、四组 SVG 正常完成构建、键盘能够操作菜单。

**为什么重要：** 工业化交付依赖可重复验证的结果，而不是开发者的口头保证。

## 构建与架构

### Static Site（静态网站）

**是什么：** 服务器直接发送已经生成的 HTML、CSS、JavaScript 和图片，不需要为每次访问实时查询数据库或执行后端业务。

**在 Will-web 中：** 个人介绍、项目、奖项证据和外部链接都适合静态托管。当前没有账户、数据库、支付或私钥调用，因此不需要后端。

**为什么重要：** 静态站部署简单、攻击面较小、成本低，也完全可以拥有高级交互和完整工程体系。

### Vite

**是什么：** 前端开发服务器和构建工具。它负责在开发阶段加载模块，并在发布前生成经过处理的静态文件。

**在 Will-web 中：** Vite 用于拆分脚本、打包本地依赖、生成 `dist/` 产物和提供可复现预览，不用于把网站改写成 React 或模板站。

**为什么重要：** 当前页面直接串联多个 CDN 脚本，版本和加载失败较难控制；正式构建可以把依赖版本和产物纳入测试。

### Build Artifact / `dist`

**是什么：** 源代码经过构建后得到的可部署文件集合，也称构建产物。

**在 Will-web 中：** Vite 最终输出的 `dist/` 仍然只包含静态 HTML、CSS、JavaScript 和资源文件，可直接交给 Vercel。

**为什么重要：** 测试和部署同一份产物，可以减少“本地正常、线上不同”的环境偏差。

### DOM（文档对象模型）

**是什么：** 浏览器把 HTML 解析成的页面结构树。JavaScript、CSS 选择器和辅助技术都通过它理解页面。

**在 Will-web 中：** 现有动效依赖具体类名、层级、固定断句和蒙版节点。随意改变 DOM 可能让横向动画或 reveal timing 失效。

**为什么重要：** 因此 Vite 接入阶段先保持 DOM 不变，语义重构单独进行并做视觉回归。

### Runtime Dependency（运行时依赖）

**是什么：** 页面在访客浏览器中执行功能时需要的外部代码库。

**在 Will-web 中：** GSAP、ScrollTrigger、SplitText、Lenis、anime.js、Webflow runtime 和 Unicorn Studio 都属于运行时依赖。

**为什么重要：** 依赖声明或 `<script>` 标签存在，不代表访客一定成功下载和执行；预加载器事故正是由第三方运行时不可用触发。

### Dependency Localization（依赖本地化）

**是什么：** 将关键库固定版本并纳入本站构建产物，由与网站相同的部署链路提供，而不是在运行时临时访问公共 CDN。

**在 Will-web 中：** 计划逐步本地打包 GSAP、Lenis 和 anime.js，同时删除没有实际用途的插件。

**为什么重要：** 它减少第三方 CDN 故障、版本漂移和供应链变化对首屏体验的影响。

## 可靠性与测试

### Fail-open（失败时开放）

**是什么：** 增强功能失败时，系统自动退回仍可使用的基础状态，而不是把用户永远挡在错误界面外。

**在 Will-web 中：** 动画库不可用时，预加载器会自动移除、导航恢复、滚动解锁，页面内容仍可阅读。

**为什么重要：** 品牌动画是增强体验，不能成为进入内容的单点故障。

### Watchdog（看门狗）

**是什么：** 在限定时间内等待正常流程完成，超时后主动触发恢复操作的保护机制。

**在 Will-web 中：** 预加载器有 8 秒 watchdog；即使依赖检测遗漏某种异常，也会最终释放页面。

**为什么重要：** 它为未知故障提供最后一道兜底，但不能替代依赖检测和测试。

### CI（持续集成）

**是什么：** 每次提交或合并请求时，在统一环境自动执行构建、测试和检查。

**在 Will-web 中：** 目标是让静态内容测试、Vite 构建和关键 Playwright QA 在进入主分支前自动运行。

**为什么重要：** 它把个人记忆中的检查步骤变成团队和 AI 都不能跳过的质量门槛。

### E2E / Playwright

**是什么：** End-to-End 测试从真实浏览器角度操作和观察完整页面；Playwright 是当前使用的浏览器自动化工具。

**在 Will-web 中：** QA 会检查六档宽度、外部资源阻断、预加载释放、证据文件、SVG 动画、reduced-motion 和横向结尾覆盖。

**为什么重要：** 动效和响应式问题通常无法仅靠搜索源码发现，必须观察浏览器计算后的真实状态。

### Visual Regression（视觉回归）

**是什么：** 将修改后的截图或关键动画帧与已确认基线比较，发现布局、裁切、时序和样式意外变化。

**在 Will-web 中：** 横向 SVG、结尾页、瀑布蒙版和 Methods & Skills 的入场不能只靠单元测试验证。

**为什么重要：** “代码执行成功”不等于品牌体验没有退化。

### `prefers-reduced-motion`

**是什么：** 操作系统提供的用户偏好，表示用户希望减少非必要动画。

**在 Will-web 中：** reduced-motion 模式仍需展示全部文字、图标和线条，但可以直接进入稳定终态。

**为什么重要：** 可访问性降级应保留内容和功能，同时正常模式继续保有品牌动效。

## 发布与安全

### Preview Deployment（预览部署）

**是什么：** 与生产环境隔离的线上版本，用于在真实托管条件下审核即将发布的代码。

**在 Will-web 中：** 每个高风险阶段先生成 Vercel Preview，确认视觉、外部资源和响应头后，才可能进入生产。

**为什么重要：** 本机验证无法完全覆盖 CDN、缓存、域名和托管平台行为。

### Rollback（回滚）

**是什么：** 发生事故时恢复到上一份已知可靠代码或部署，而不是继续在线修补未知状态。

**在 Will-web 中：** 每阶段独立提交；生产异常时优先恢复上一份 Vercel 部署，再定位并回滚对应提交。

**为什么重要：** 快速恢复用户可用性通常比在故障现场继续修改更安全。

### CSP（内容安全策略）

**是什么：** 浏览器响应头策略，用来限制页面允许执行脚本、加载图片和连接的来源。

**在 Will-web 中：** 当前大量内联代码和第三方脚本使严格 CSP 难以直接启用；应先收敛依赖，再用 Report-Only 观察，最后才强制执行。

**为什么重要：** 一次性开启过严策略可能再次造成脚本被浏览器阻断，因此安全策略本身也需要渐进迁移和回滚。
